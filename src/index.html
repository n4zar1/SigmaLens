SigmaLens guide

SigmaLens is a small SIEM that runs inside this page. You load event logs, hunt through them with a search bar, and write Sigma rules that are tested against the data while you type. It never connects to the internet, and your files never leave your computer.

Examples marked Try it run against the loaded data. They were written for the demo dataset:

Getting started

  1. Click Open files (or drag files onto the page) and pick your logs: .json / .jsonl.
  2. Go to Search and type a query, or just scroll through the timeline.
  3. Found something interesting? Turn it into a rule in the Sigma editor and check that it matches what you expect, and nothing else.

You can load more files at any time. Events are added to what is already loaded, and Sigma rules (.yml) go to the Rules tab. If you load a file that is already loaded (or a copy of it with another name), SigmaLens skips it and tells you, so no event is counted twice.

Loading data

SigmaLens reads JSON objects, one event each:

  • JSONL (one object per line): the recommended format.
  • A JSON array of objects.
  • Files that wrap the events: CloudTrail / Azure exports ({"Records":[…]}) and Proofpoint TAP SIEM API responses ({"messagesDelivered":[…],"clicksPermitted":[…]…}). Each TAP event gets a tap_event field with the list it came from.
  • .eml files: one event per message, with every header as a field (repeated headers such as Received are joined with line breaks) plus an analysis under eml.*: eml.from_domain, eml.return_path_domain, eml.reply_to_domain, eml.spf / eml.dkim / eml.dmarc (from the top Authentication-Results), eml.received_ips, eml.origin_ip (the bottom-most public hop), eml.urls, eml.url_domains, eml.attachments, eml.attachment_types, eml.attachment_sha256 and eml.body.
  • evtx_dump / python-evtx output ({"Event":{"System":…,"EventData":…}}), which is flattened automatically: EventID, Channel, Computer, EventRecordID, Provider and @timestamp come from System, and every EventData value becomes its own field.

Other nested objects become dotted names, for example userIdentity.arn. Lists of objects are kept as JSON and also get one field per key with the values joined: threatsInfoMap.classification = phish, malware (use |contains on those). The event time is taken from the first field present among @timestamp, TimeCreated, SystemTime, UtcTime, timestamp, time, eventTime, TimeGenerated, CreationTime, createdDateTime, published, messageTime, clickTime, ts and __REALTIME_TIMESTAMP (epoch seconds, milliseconds and microseconds work too), or from W3C date + time. A time without a zone is read as UTC, and all times on screen are UTC.

Converting .evtx files

Browsers can't read the binary .evtx format, so convert them first. On Windows, the bundled script uses only built-in cmdlets:

.\tools\evtx2jsonl.ps1 -Path .\Logs\*.evtx -OutDir .\jsonl

It writes one .jsonl per log, with the same field names you see in Event Viewer's XML view (for Sysmon: Image, CommandLine, ParentImage…).

Reading the results table

Each row shows the time, the log it came from (Sysmon, Security, PowerShell…), the event ID and a Details summary chosen per event type: the command line for a process, Image → IP:port for a connection, the query for DNS, the key and value for the registry, the script for PowerShell 4104.

When you load data, SigmaLens also adds the Host, User and Source IP columns if most events have them. Every source names these fields differently (Computer, _HOSTNAME, userIdentity.arn, sourceIPAddress, ClientIP…), so each cell is filled from the right field for that event. That way a mixed dataset still lines up. Click × in a column header to hide it. These columns are also exported to CSV.

Click a row to see every field. Next to each value you'll find three buttons:

  • + keeps only events with this value: it adds Field:"value" to the search.
  • − hides events with this value: it adds NOT Field:"value".
  • σ copies the field as a Sigma line (Field: 'value'), ready to paste into a rule.

Click the Time header to flip the sort order. Export CSV saves the current results.

Search syntax

The search language is close to Kibana and Lucene. Searches are case-insensitive, both for field names and for values.

QueryMeaning
EventID:1Field equals the value (the whole value, not part of it).
Image:*\powershell.exe* is a wildcard. *text* means "contains", text* "starts with", *text "ends with".
CommandLine:"*-w hidden*"Quotes keep spaces inside one value. Wildcards still work inside quotes.
whoamiFree text: any field contains the word.
EventID:22 AND NOT QueryName:*.corp.exampleAND, OR, NOT in capitals, or && || !. A leading - also negates. Two terms side by side mean AND.
(EventID:3 OR EventID:22) Image:*updsvc*Parentheses group conditions.
DestinationPort:>=1024Numeric comparison: > >= < <=.
_exists_:ScriptBlockTextThe field is present and not empty. Field:* does the same.
_source_:linuxEvents recognised as that source: a product (aws, linux…), a service (sshd, cloudtrail…), a category (proxy, webserver…) or the label in the Source column. Wildcards work.

Equals vs contains. CommandLine:whoami only matches a command line that is exactly whoami. To find it anywhere in the command line use CommandLine:*whoami*, or plain whoami to look in every field.

Backslashes are ordinary characters in the search bar: type Windows paths as they are, C:\Windows\System32\*.

Timeline & fields

The timeline shows how the matching events spread over time. Bar width adapts to the span (1 second up to 1 week). Hover a bar to see its count, and click it to zoom: the From/To boxes take that bar's range. Reset clears the query and the time range.

The fields panel lists every field in the current results and the share of events that have it. Click a field to see its 10 most common values and the number of distinct values, then use + / − to filter or Add as column to show it in the table. Spotting rare values is often the fastest way to find the attacker: try EventID:1 and look at the values of ParentImage.

Sigma editor

Sigma is an open, vendor-neutral format for detection rules. A rule says which logs to read (logsource), what to look for (named search identifiers under detection) and how to combine them (condition):

title: Discovery from PowerShell
logsource:
    category: process_creation    # which events (see Logsource mapping)
    product: windows
detection:
    parent:                       # a search identifier: all fields must match (AND)
        ParentImage|endswith: '\powershell.exe'
    tools:                        # a list of maps: any of them may match (OR)
        - Image|endswith: '\nltest.exe'
        - CommandLine|contains: 'Domain Admins'
    condition: parent and tools
level: medium

  • Run (or Ctrl+Enter) tests the rule against all loaded events. The time range on the Search tab doesn't apply here.
  • With live checked, the rule runs again shortly after you stop typing.
  • Under the editor you see the rule's title and level, and Reads: the exact events its logsource selects. If something is wrong (bad indentation, an unknown identifier in the condition, an unsupported modifier) the error is shown there and its line number turns red.
  • Save to Rules stores the rule in the Rules tab. If you opened it from there, it updates it in place.
  • Show in Search sends the matches to the Search tab, where you can use the timeline and fields panel on them.

The editor remembers your last rule in this browser.

Modifiers & values

Write a field as Field|modifier. A list of values means any of them. Matching is case-insensitive unless you add |cased.

ModifierMatches when the field…
(none)equals the value (wildcards allowed)
containscontains the value
startswith / endswithstarts / ends with the value
allmatches every value in the list instead of any (e.g. CommandLine|contains|all)
rematches a JavaScript regular expression; add i, m, s for flags (|re|i)
windashalso tries / and the long dashes wherever the value has a - flag (-enc, /enc, –enc…)
casedmatches with exact capitalization
existsis present (true) or absent (false)
gt gte lt lteis a number above / below the value
cidris an IPv4 address inside the range (10.0.0.0/8)

Wildcards and escaping

In Sigma values, * matches any text and ? one character. A backslash only escapes those characters and itself: \* is a literal asterisk and \\ one literal backslash. Any other backslash is literal, so paths are written as usual: 'C:\Users\Public\'.

Common trap: 'C:\Users\*' does not mean "anything under C:\Users": \* is an escaped asterisk. Write Image|startswith: 'C:\Users\' or 'C:\Users\\*'.

Empty and missing fields

Field: null matches when the field is missing or empty. A condition like not filter on a field that some events don't have will let those events through. That's a frequent source of false negatives worth testing.

Conditions

selectionone search identifier
selection and not filterand, or, not, with parentheses for grouping
1 of selection_*at least one identifier whose name matches the pattern
all of selection_*every identifier matching the pattern
1 of them / all of themany / every identifier (names starting with _ are left out)

A search identifier can also be a plain list of strings (keywords). It matches when any field of the event contains any of them.

Other sources

Events that are not Windows are recognised by the fields they have, so no configuration is needed. This is what each logsource reads. A rule for product: aws only reads CloudTrail events, even if the same session also holds Windows or Linux logs. The Source column of the results shows what each event was recognised as, and you can search by it with _source_:, for example _source_:linux, _source_:sshd or _source_:proxy.

The Mapping selector in the top bar changes what process_creation reads. It is chosen automatically when you load data: Sysmon if the logs have Sysmon event 1, Security if they have 4688, or both if they have both. You can still change it by hand.

  • Sysmon (default): Sysmon event 1.
  • Security: Security event 4688. Image, ParentImage, ProcessId and User are filled from NewProcessName, ParentProcessName, NewProcessId and SubjectDomainName\SubjectUserName. Fields that only Sysmon has (OriginalFileName, Hashes…) stay empty.
  • Both: either source. One process may then match twice.

Rules view

Load one or many .yml files (a file may hold several rules separated by ---) and press Run all. Each rule shows its level, the events it reads and its hit count. Rules that fail to parse show the error instead. Open takes a rule to the editor, and ✕ removes it from the list (not from disk). Changing the Mapping re-checks every rule.

Workflow: from a hunt to a rule

A typical loop, using the demo dataset:

  1. Find something odd. Search for processes started by PowerShell:
  2. Understand it. Open the rows and read the command lines. Use the timeline to see what happened just before and after.
  3. Describe it as a rule. Copy the key fields with σ, paste them into the Sigma editor and generalize: endswith instead of a full path, a list instead of a single value.
  4. Check true positives. The rule must match the malicious events you found.
  5. Check false positives. Look at everything else it matches. Too much? Add a precise filter.
  6. Check false negatives. Ask how an attacker could do the same thing and not match: a renamed binary, another file type, a different tool, a split command line. Test those variants too.

Limits & privacy

  • Not supported: aggregations (| count() by …, timeframe), correlation rules, and the base64, base64offset, utf16le and wide modifiers. They're reported as errors, never silently ignored.
  • Everything is kept in memory. A few hundred thousand events work well on a normal laptop. Very large datasets are slower to search, and the live editor turns itself off above 300,000 events (use Run).
  • Nothing is uploaded and no network requests are made. Only your preferences (last query, last rule, mapping, theme, tab) are stored in this browser's local storage.

Sigma

Supports maps and lists of maps, keyword lists, condition with and/or/not, parentheses, 1 of x*, all of them; modifiers contains startswith endswith all re i m s cased exists gt gte lt lte cidr windash. Values use Sigma escaping: * and ? are wildcards, \* is a literal asterisk. Not supported: aggregations, correlations, base64 modifiers.
